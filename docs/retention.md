# Data retention

Spec §12 says to keep data only as long as it is needed and to enforce every deadline with a job. This page lists each kind of data we store, how long it is kept, and what deletes it. The defaults are below. Each setting can be shortened with the environment variable named, and none can be lengthened past the limit shown.

Everything in the database and object storage is deleted by the **retention pass**: `apps/api/src/purge/retention-pass.ts`, run every `MEDIA_PURGE_INTERVAL_MINUTES` (default 15). A database lock stops two API instances running it at the same time. It logs counts only, never keys or content.

Pupils who open a class link (ADR 0027) have no account and nothing about them is stored. The join code travels with their lesson and tutor requests and is checked against the stored hash, then forgotten. A class lesson is served without its `assumptions`.

A lesson a learner shares (ADR 0021) is an anonymous copy: no assumptions, contact details redacted, nothing tied to the account. So it stays after the account is deleted, like any other lesson.

Lessons, review events, sources and the rights register hold no learner data (apart from the assumptions exception below), so they are kept for as long as they are useful as content and evidence. A lesson is shared (`cacheScope: shared`) only when a learner shares it and a reviewer approves it (ADR 0021). A private lesson keeps the learner's question only as a hash. The one exception is `assumptions`: if an API client sends them with a request ("I live at sea level"), they are stored as text in that lesson, are not tied to any account, and stay with it. The web app sends none, and a shared copy drops them (ADR 0021).

## Outside the database

These are set in hosting, not in this repo, so no job enforces them. The launch review (#74) must confirm each one.

| Data                                                                                                                            | Kept for                                                                                     | Where to set it                                 |
| ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Application logs, including LLM call telemetry: model, prompt version, token counts and latency, never message text             | 30 days                                                                                      | The log store's retention setting               |
| Database backups                                                                                                                | 30 days rolling, so a deleted row is gone from every backup within 30 days                   | The database host's backup policy               |
| Object storage (photos)                                                                                                         | Not backed up and not versioned, so a deleted photo cannot come back                         | Bucket settings: versioning off, no replication |

| Browser `sessionStorage`: depth, age band and the tutor's per-visit id                                                          | Until the tab closes                                                                         | —                                               |

## Promises this page backs

- The privacy page, capture page and home page say a photo is deleted within 7 days, or sooner once recognised, unless the learner keeps it. `MEDIA_TTL_ORIGINAL_DAYS` therefore cannot be set above 7.
- The privacy page says anything typed in a report is deleted after 90 days (`FEEDBACK_DETAILS_RETENTION_DAYS`).
- The privacy page says a signed-in learner's tutor conversations are kept 30 days and a signed-out one's for the visit. `TUTOR_TTL_ACCOUNT_DAYS` therefore cannot be set above 30.

If a default here changes, update those pages in the same pull request.

## Deleting an account

`POST /account/delete` runs straight away, once the learner types the account's email:

1. Each linked photo is deleted with `deleteOnRequest`: bytes first, then the registry row, then an audit entry, "deleted at the learner's request". If storage fails, nothing else is deleted, so the learner can try again.
2. In one transaction, it deletes the classes and their lesson lists, the teaching-tools flag, the saved lessons, tutor turns, email links, sessions and the account row.
3. The session cookie is cleared.

Backups roll over within 30 days (above), so a deleted account is gone from every copy by then. Recognition results, feedback and tutor turns asked while signed out were never tied to the account, so they follow their own schedules in the table. `GET /account/export` returns everything that is tied to the account, including the tutor conversations and a download for each linked photo.

## Resetting a tutor conversation

`POST /tutor/conversation/reset` deletes one lesson's conversation straight away: the turns of this visit and, when signed in, the account's turns for that lesson. Nothing else is kept from them.
